## TREE FOUNDATIONS — COVERED APR 6 (do not re-explain unless asked)

### What a node is
- `TreeNode` struct: `val`, `left`, `right`
- `left` and `right` are pointers (addresses), not values
- `NULL` means no node exists in that direction
- `: val(x), left(nullptr)` constructor = `this->val = x`

### Recursion on trees — 5-step formula
```
1. Base case      → if (root == nullptr) return SOMETHING
2. Go left        → recurse on root->left
3. Go right       → recurse on root->right
4. Combine        → use left and right answers
5. Return         → send answer up
```

### LC #226 — Invert Binary Tree ✅
```cpp
TreeNode* invertTree(TreeNode* root) {
    if (root == nullptr) return nullptr;
    TreeNode* left = invertTree(root->left);
    TreeNode* right = invertTree(root->right);
    root->left = right;
    root->right = left;
    return root;
}
```
**Mistake made:** wrote `invertTree(left)` instead of `invertTree(root->left)`

### LC #104 — Max Depth ✅
```cpp
int maxDepth(TreeNode* root) {
    if (root == nullptr) return 0;
    int left = maxDepth(root->left);
    int right = maxDepth(root->right);
    return max(left, right) + 1;
}
```
**Key insight:** base case returns 0 — nullptr is not a node.

### LC #100 — Same Tree ✅
```cpp
bool isSameTree(TreeNode* p, TreeNode* q) {
    if (p == nullptr && q == nullptr) return true;
    else if (p == nullptr || q == nullptr) return false;
    else if (p->val != q->val) return false;
    bool left  = isSameTree(p->left,  q->left);
    bool right = isSameTree(p->right, q->right);
    return left && right;
}
```
**Mistakes made:** `p != q` instead of `p->val != q->val` — comparing pointers not values. `root->value` instead of `root->val`. Null check must come before value access or it crashes.

### LC #572 — Subtree of Another Tree ✅
```cpp
bool isSubtree(TreeNode* root, TreeNode* subRoot) {
    if (root == nullptr) return false;
    if (root->val == subRoot->val) {
        if (isSameTree(root, subRoot)) return true;
    }
    bool left  = isSubtree(root->left,  subRoot);
    bool right = isSubtree(root->right, subRoot);
    return left || right;
}
```
**Mistakes made:** `return left && right` instead of `|| right` — subRoot only needs to exist on ONE side. `isSameTree` return not handled correctly at first — returned true unconditionally.

## AUTH FOUNDATIONS — COVERED APR 7 (do not re-explain unless asked)

### API Key auth
- Client sends `X-API-Key` header with every request
- Server checks against expected value using `verify_api_key()`
- Wrong or missing → 401
- Added to both `GET /users` and `POST /users`

### JWT auth
- Client sends username + password to `POST /login`
- Server verifies credentials, generates signed JWT using `python-jose`
- JWT structure: `header.payload.signature`
- `sub` field = username, `exp` field = expiry (30 min)
- Client sends JWT to protected routes
- Server calls `jwt.decode()` — verifies signature mathematically, no DB lookup
- Tampered or expired token → `JWTError` → 401
- Protected route: `GET /protected?token=...`

### Key concepts
- 401 = not authenticated (I don't know who you are)
- 403 = not authorized (I know you but you can't do this)
- API keys: best for devices/services
- JWT: best for users/sessions — stateless, expiry built in
- Changing JWT payload breaks the signature — that's the security guarantee

### FastAPI auth setup

## HTTP/HTTPS + TLS — COVERED APR 9 (do not re-explain unless asked)

### HTTP vs HTTPS
- HTTP = no security. Data sent in plain text — anyone intercepting can read it
- HTTPS = HTTP + TLS (Transport Layer Security) layer on top
- TLS provides three guarantees:
  - **Confidentiality** — data is encrypted, no one can read it in transit
  - **Integrity** — tampering is detected
  - **Authentication** — you're talking to the real server, not an imposter

### TLS Handshake — step by step
```
Client                                    Server
  |                                          |
  |--------- 1. Client Hello -------------->|
  |        (supported encryption methods)   |
  |                                          |
  |<-------- 2. Server Hello + Certificate -|
  |        (contains server's public key)   |
  |                                          |
  |  [client verifies certificate with CA]  |
  |                                          |
  |--------- 3. Session Key --------------->|
  |        (encrypted with server public key)|
  |                                          |
  |  [server decrypts with private key]     |
  |                                          |
  |<======== 4. Encrypted HTTP data =======>|
  |        (symmetric AES encryption)       |
```

### Key concepts
- **CA (Certificate Authority)** — trusted third party that signs server certificates. Browser has a built-in list of trusted CAs. If certificate is not signed by a trusted CA → browser warns and blocks.
- **Public key** — shared openly. Used to encrypt the session key.
- **Private key** — stays on server, never shared. Used to decrypt the session key.
- **Session key** — random symmetric key generated per connection. Used for all actual data encryption.
- **Asymmetric encryption** (public/private key) — used once, only to exchange the session key. Slow.
- **Symmetric encryption** (AES) — used for all data after handshake. Fast.
- Why switch to symmetric? Public/private key encryption is expensive — doing it every request would be too slow.

### openssl hands-on ✅
```bash
openssl s_client -connect google.com:443
```
- `CN=*.google.com` — wildcard certificate, covers all google.com subdomains
- `TLSv1.3` — TLS version in use
- `TLS_AES_256_GCM_SHA384` — cipher suite: AES256 encryption + SHA384 integrity check
- Certificate chain visible — leaf cert → intermediate CA → root CA

### MITM (Man in the Middle) — why HTTPS prevents it
- Can't fake certificate — CA only issues certs to verified owners. Fake cert → browser blocks.
- Can't decrypt data — session key encrypted with server's public key. Only server's private key can decrypt. MITM has neither.

### IoT connection
- AWS IoT Core uses **mTLS (mutual TLS)** — both server AND device present certificates
- Device gets its own certificate + private key when provisioned
- Both sides verify each other — not just client trusting server
